# Agent Guidelines

This file provides guidance when working with code in this repository.

## Project Overview

See this projects README.md for an overview of the project, and ADR documents in docs/adr/ for architectural decisions.

## Development Commands

**IMPORTANT**: Always use the Makefile commands for development tasks.

### Setup
```bash
make setup  # Set up venv and sync dependencies with uv
```

### Testing
```bash
make test                                    # Run all tests with pytest and coverage
uv run pytest tests/test_foo.py             # Run specific test file
uv run pytest tests/test_foo.py::test_name  # Run specific test
uv run pytest -v                             # Verbose output
```

### Code Quality
```bash
make lint   # Check code with ruff
make fix    # Auto-fix ruff issues
make type   # Type check with mypy (strict mode)
make radon  # Check cyclomatic complexity and maintainability
make ci     # Run all CI checks (lint + type + test + radon)
```

**Before completing any feature**, run `make ci` to ensure all checks pass.

## Code Quality Requirements

Writing guidance:

- Only include a brief description of the thing in docstrings (no arguments or return types)
- Do not use docstrings at the beginning of files.

## Project Structure

```
slarti/         # Main package source code
tests/          # Test files (mirror slarti/ structure)
docs/slarti/    # The architecture model slarti checks itself against
docs/adr/       # Architecture Decision Records
docs/architecture.md  # Generated in part by slarti itself
```

## The architecture model (slarti dogfoods itself)

This repository is checked by its own tool. Before committing a change that
touches structure or domain entities, run:

```bash
slartiarch check        # the seams: OWN-*, REG-*, DOC-* (the drift gate CI runs)
slartiarch check --fix  # regenerate the diagrams and tables, then check
```

### Files you may edit

- `docs/slarti/instances/*.yaml` — slarti's own elements and relations, as
  vocabulary instances typed with the C4 profile
- `docs/slarti/linkml/slarti.yaml` — the LinkML schema of slarti's domain entities
- `docs/slarti/shacl/*.ttl` — hand-written SHACL
- `docs/slarti/constraints.yaml` — the rule registry
- `docs/slarti/data/valid/*`, `docs/slarti/data/invalid/*` — fixtures, one per rule
- prose and the hand-written Mermaid diagrams **outside** generated regions in
  `docs/architecture.md`

### Files you must never edit

- anything between `<!-- slarti:begin ... -->` and `<!-- slarti:end ... -->`

Those regions are regenerated by `slartiarch check --fix`; hand edits are reported
as `DOC-1` and block the merge.

### Rules

- A new domain class needs an `owner` annotation naming an element in
  `docs/slarti/instances/`, and that element must list the class in its `owns`
  (`OWN-1`..`OWN-5`).
- A new element or relation should be drawn in the context or containers diagram
  in `docs/architecture.md`; every `Rel` there must be a declared relation
  (`DANGLE-2`).
- A new SHACL shape needs a constraint in `docs/slarti/constraints.yaml` referencing
  it, and a fixture under `docs/slarti/data/invalid/` that makes it fire
  (`REG-2`, `REG-6`, `REG-7`).
- Every diagram node and edge in vocabulary instances is attached (`element` /
  `relation`) or `ignored` with a reason (`ATTACH-*`, `IDENT-*`, `DANGLE-*`,
  `DRAWN-1`).
- A rule that cannot be mechanically enforced is written as `enforced_by: none`
  with a `reason`. That is honest, not a failure.
- `slartiarch report --json` describes every rule, shape, owned class and check ID,
  each check with its remedy.
